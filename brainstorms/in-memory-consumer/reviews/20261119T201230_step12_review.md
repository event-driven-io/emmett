### Step-1. No test checks that a checkpoint is read back from the custom database

Quote: spec: "`mongoDBCheckpointer` reads and stores them in that database's `emt:processors` collection". Diff: `readProcessorCheckpoint(context.session.client, { ...options, databaseName: checkpointerOptions.databaseName })`. Test 20.5 only runs a fresh processor once, then calls `readProcessorCheckpoint(client, { processorId, databaseName: customDatabase.databaseName })` itself.
Consequence: On a fresh processor, `read` returns null from either database, so 20.5 still passes if `read` drops `databaseName`. With that bug, a restarted processor on a custom-database store would read null, reprocess from the beginning, and then get `MISMATCH` against the checkpoint stored in `custom_db`. No step 12 test runs the read path with an existing checkpoint, for example by restarting a processor with the same `processorId` and checking it resumes after the stored checkpoint.
Belongs to: plan
Resolution: fixed: spec.md decides reads too ("reads and stores them in that database's `emt:processors`"), so treated as implementation. Added "reactor on a custom-database store resumes from its checkpoint in the custom database"; it fails when `read` drops the database name.

### Step-2. Nothing tests that projectors and workflow processors follow `storage` for checkpoints

Quote: spec: "MongoDB reactors, projectors and workflow processors get an optional `storage` option. The consumer's factories fill it with the consumer's `storage` when the caller gave none" and "MongoDB processor checkpoints follow `storage.databaseName`". Diff: `projectorFactory: (processorOptions) => mongoDBProjector({ ...processorOptions, storage: processorOptions.storage ?? options.storage })`, `mongoDBProjector` → `mongoDBCheckpointer<EventType>({ databaseName: mongoDBStorageDatabaseName(options.storage) })`, and the same in `mongoDBWorkflowProcessor`. Tests 20.1-20.8 use only reactors and one workflow, and only 20.5 (a reactor) checks where the checkpoint lands.
Consequence: Projectors don't use `session.messageStore` (Q31), so where their checkpoint lands is the only visible effect of their `storage`. If `projectorFactory` stopped filling `storage`, or `mongoDBProjector` stopped passing `databaseName`, projector checkpoints would go to the default database and no test would fail. The same goes for the workflow checkpointer's `databaseName`, and for a caller-given `storage` on `consumer.workflowProcessor`/`consumer.projector`. The step's tests list leaves out a case the spec decides.
Belongs to: plan
Resolution: fixed: spec.md names reactors, projectors and workflow processors, so treated as implementation. Added projector and workflow processor checkpoint tests; each fails when its consumer factory stops filling `storage`.

### Step-3. The MongoDB checkpointer takes the database as a factory option, not from the handler context as PostgreSQL does

Quote: spec: "`mongoDBCheckpointer` reads and stores them in that database's `emt:processors` collection instead of the client's default database, as PostgreSQL's checkpointer follows `migrationOptions.databaseSchemaName`". PostgreSQL: `postgreSQLCheckpointer = <...>(): PostgreSQLCheckpointer<...> => ({ read: async (options, context) => ... databaseSchemaName: context.migrationOptions?.databaseSchemaName`. Diff: `export const mongoDBCheckpointer = <MessageType extends Message = Message>(checkpointerOptions: { databaseName?: string } = {})`.
Consequence: PostgreSQL's checkpointer takes no arguments and reads the schema from the processing context. The MongoDB one changes its exported signature and only follows storage when the caller passes `databaseName`. A caller who uses the exported `mongoDBCheckpointer()` in a custom processor on a custom-database store still reads and writes the default database. This breaks the standing driver-consistency rule that the r13 note relies on ("resolved by the standing consistency rule (PostgreSQL's checkpointer follows `migrationOptions.databaseSchemaName`)").
Belongs to: implementation
Resolution: fixed: `mongoDBCheckpointer()` takes no arguments again and reads `context.storage`, set by the processing scopes on a new optional `storage` field of `MongoDBProcessorHandlerContext`, as PostgreSQL reads `context.migrationOptions`.

### Step-4. New public export `mongoDBStorageDatabaseName`

Quote: diff, storage/mongoDBEventStoreStorage.ts: `export const mongoDBStorageDatabaseName = (storage: MongoDBEventStoreStorageOptions | undefined): string | undefined => typeof storage === 'object' ? storage.databaseName : undefined;`. storage/index.ts: `export * from './mongoDBEventStoreStorage';`, re-exported through eventStore/index.ts and the package index.ts.
Consequence: The package gains a public function that neither the step nor the spec asks for. Users can import it, so removing or renaming it later is a breaking change. The step only needs `storage.databaseName` passed to the source and checkpointer, which an internal, non-exported helper (or an inline expression) would do. This is a change the step does not ask for (f).
Belongs to: implementation
Resolution: fixed: helper removed; the consumer reads `storage.databaseName` inline and the checkpointer uses a private helper.
