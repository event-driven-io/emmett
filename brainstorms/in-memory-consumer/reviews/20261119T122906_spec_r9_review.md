### Q&A-1. MongoDB reactors and projectors take `messageStore` from the consumer session, unlike every other store's processors

Quote: "MongoDB reactors and projectors, which only spread the consumer's session, now also receive it." / "`MongoDBProcessorHandlerContext` ... declare `session.messageStore` as required" / Q34 explanation "Every store's processors build `messageStore` themselves and always have it."
Consequence: `mongoDBProcessingScope` (`mongoDBProcessor.ts:102-122`) spreads a `Partial` session, so it stops compiling under the required type; a processor with its own client would get `session.client` and `session.messageStore` from different clients; outside the MongoDB consumer it gets nothing.
Belongs to: spec
Resolution: fixed in r10. Precedent: the MongoDB workflow processing scope builds it from the processor's client (`mongoDBProcessor.ts:137-141`), as SQLite, PostgreSQL and EventStoreDB processors do. The MongoDB reactor/projector scope builds it from the processor's own client, once at processor creation (hot-path rule).

### Q&A-2. A MongoDB `messageStore` built from the client alone ignores the store's `storage` options

Quote: "MongoDB builds it from the consumer's client" / ACs 9.10, 9.11 "that event can be read from the MongoDB store".
Consequence: `MongoDBEventStoreOptions.storage` (`mongoDBEventStore.ts:196`) doesn't reach the consumer (`mongoDBEventStore.ts:546-556`), so with non-default storage, appends through `session.messageStore` land in default storage. The MongoDB workflow scope behaves the same today (`mongoDBProcessor.ts:140`).
Belongs to: qa
Resolution: fixed in r11 (Q36: Oskar asked "how pg does it?"; resolved by matching PostgreSQL, which passes its schema settings through to every processor's message store)

### Quality-2. AC 9.13 expects the failure "when it handles a message", but the scope runs at `start`, and a direct `handle(...)` before `start` does nothing

Quote: AC 9.13 / "through a direct `handle(...)` call."
Consequence: `start` runs `processingScope` to read the checkpoint (`processors.ts:909-916`), so on a generic consumer without a scope `start()`/`whenStarted()` reject first; `handle` on a not-started processor returns at once (`processors.ts:1016`).
Belongs to: spec
Resolution: fixed in r10. AC 9.13 now expects `start()` and `whenStarted()` to reject; the "direct `handle(...)`" example is removed.
