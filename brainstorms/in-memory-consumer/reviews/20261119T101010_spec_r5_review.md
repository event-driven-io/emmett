### Q&A-1. How `session.messageStore` is typed in the in-memory handler context is not stated

Quote: "every in-memory processor the consumer creates from options gets `context.session.messageStore` set to the consumer's `messageStore`, as SQLite's and PostgreSQL's processing scopes do" / ACs 9.5, 9.6 / Q30 "it should just behave consistently to how sqlite and postgresl behaves"
Consequence: SQLite and PostgreSQL declare it in their context types (`messageStore: SQLiteEventStore`, `sqliteProcessor.ts:92`; `messageStore: PostgresEventStore`, `postgreSQLProcessor.ts:102`). `InMemoryProcessorHandlerContext` is `MessageHandlerContext<{ database }>` with `session` as `DefaultRecord`, so handlers read an untyped value. A developer has to guess whether to change the public type, and whether to use `EventStore` or `InMemoryEventStore`.
Belongs to: qa (type choice)
Resolution: fixed in r6 (back to brainstorm: Q31 "Yes, reactors should get it too", Q32 "yes"; typing derived from Q32, flagged to Oskar)

### Q&A-2. Whether already built processors also get `session.messageStore` is not stated

Quote: "every in-memory processor the consumer creates from options gets `context.session.messageStore`" / "Already built processors passed in are not changed." (said about the database)
Consequence: Through the consumer `scope` (as SQLite passes `session`, `sqliteEventStoreConsumer.ts:259-267`; applied to every processor, `consumers.ts:229-244`; spread by `inMemoryProcessingScope`, `inMemoryProcessors.ts:179-183`), built processors also get it. Inside each created processor, `inMemoryReactor`/`inMemoryProjector` have no option for it today, so one must be added. A handler on a built processor sees a different context depending on the choice.
Belongs to: qa
Resolution: fixed in r6 (back to brainstorm: Q32 "yes")

### Quality-1. How `session.messageStore` reaches processors is not stated

Quote: same as Q&A-2, plus AC 11.10 "an already built processor passed to `consumer.reactor(processor)` ... keeps using its own storage."
Consequence: Same choice as Q&A-2: (a) consumer `scope`, so every processor gets it, including built and other-package ones; or (b) a new message-store option on `inMemoryReactor`/`inMemoryProjector`, set by the factories, which changes their public options. AC 11.10 does not say whether `session.messageStore` counts as "its own storage".
Belongs to: qa
Resolution: fixed in r6 (back to brainstorm: Q32 "yes")
