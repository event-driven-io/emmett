### Standards-1. The new SQLite scenarios check fewer event fields than the in-memory test of the same behaviour

Quote: identical in the sqlite3, D1 and Durable Objects specs:

```ts
events.map(({ type, data, metadata }) => ({
  type,
  data,
  streamName: metadata.streamName,
  streamPosition: metadata.streamPosition,
})),
```

The in-memory counterpart, `assertWelcomed` in `src/packages/emmett/src/eventStore/consumers/inMemoryEventStoreConsumer.messageStore.unit.spec.ts`, also maps `kind`, `schemaVersion`, `globalPosition`, `checkpoint`, `correlationId` and `causationId`, and compares them with `correlationId: handled.metadata.correlationId` and `causationId: handled.metadata.messageId`. Project rule (memory): "assert ALL fields of expected events ... Partial matching is the exception".
Consequence: The test only checks that the event can be read back. If the SQLite consumer's `messageStore` lost the handled message's trace (dropped `correlationId` and `causationId`), or wrote with the wrong kind or schema version, these tests would still pass. The SQLite tests also drift from the convention the earlier steps set for the same scenario. Spec 16.1 only requires "that event can be read from that consumer's store", so the step is not wrong; the local convention and the assert-all-fields rule are clear, and `kind`, `schemaVersion`, `correlationId` and `causationId` have known values here. If `globalPosition` and `checkpoint` are not fixed on D1 and Durable Objects because those databases may not be fresh per test, leave out only those two.
Belongs to: implementation
Resolution: fixed (all three specs now also assert kind, schemaVersion, globalPosition, checkpoint, correlationId and causationId, as assertWelcomed does)
