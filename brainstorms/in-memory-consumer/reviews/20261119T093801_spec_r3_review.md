### Q&A-1. No answer settles how the consumer tells that `messageStore` is an in-memory store

Quote: Spec: "Message-store rule for the database: when the consumer's `messageStore` is an in-memory store, every in-memory processor the consumer creates from options ... gets `messageStore.database` through `connectionOptions.database`." / "`messageStore` is an `EventStore`". Q25 B: "from `messageStore` when it's an in-memory store (`messageStore.database`), and a fresh database otherwise."
Consequence: `EventStore` has no `database`; the codebase has no type guard, brand or `isInMemoryEventStore`. Only `InMemoryEventStore` exposes `database` (`inMemoryEventStore.ts:44-46`). A developer must pick: duck-typed `'database' in messageStore`, a new brand or guard, or a typed overload. The choice changes the outcome for a wrapped in-memory store and for a user store that happens to have a `database` field.
Belongs to: qa
Resolution: fixed in r5 (back to brainstorm: Q29 "A")

### Quality-1. Nothing says how the consumer tells that `messageStore` is an in-memory store

Quote: "when the consumer's `messageStore` is an in-memory store, every in-memory processor the consumer creates from options ... gets `messageStore.database` through `connectionOptions.database`" / "`messageStore` is an `EventStore`; both are required." / AC 11.9 "GIVEN a standalone consumer whose `messageStore` is not an in-memory store ..."
Consequence: Same gap as Q&A-1. Options: check for a `database` member, add a marker to `getInMemoryEventStore`'s result (public API change), or distinguish through the static type (overload or generic). They differ for wrappers and for custom stores with a `database` field. The spec also doesn't say whether the check runs once at factory call or per processor.
Belongs to: qa
Resolution: fixed in r5 (back to brainstorm: Q29 "A")

### Quality-2. Unclear whether only `includeAsyncProjections` projectors get `context.eventStore`, or every processor on the consumer

Quote: "Async projections run by the store's consumer get the same context as inline projections: `context.eventStore` is the store and `context.database` is the store's database." / "With `includeAsyncProjections: true`, it adds each async projection as a projector whose handler context has `eventStore` set to the store" / AC 9.5
Consequence: `inMemoryProcessingScope` spreads the consumer's partial context into the handler context (`inMemoryProcessors.ts:179-183`). Adding `eventStore` in the consumer `scope` (as SQLite adds `session`/`execute`, `sqliteEventStoreConsumer.ts:259-267`) gives it to every processor, including `consumer.projector({ projection })` and processors from other packages. Adding it only to the `includeAsyncProjections` projectors means the same projection gets `context.eventStore` when registered on the store and `undefined` when passed to `consumer.projector(...)`. Also unstated: whether a standalone consumer with an in-memory `messageStore` sets `context.eventStore`.
Belongs to: qa
Resolution: fixed in r5 (back to brainstorm: Q30 "Dude, it should just behave consistently to how sqlite and postgresl behaves")
