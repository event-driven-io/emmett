### Q&A-1. The EventStoreDB consumer has no scope to add `messageStore` to

Quote: "the SQLite, PostgreSQL, MongoDB and EventStoreDB consumers each add `messageStore` to the session they pass through their `scope`."
Consequence: `eventStoreDBEventStoreConsumer` passes no `scope` (`eventStoreDBEventStoreConsumer.ts:166-187`); the default is `handler({})` (`consumers.ts:229-230`). Its `projectorFactory` is `inMemoryProjector`, so every EventStoreDB projector depends on this.
Belongs to: spec
Resolution: fixed in r9. Precedent: the MongoDB consumer's scope passes `{ session: { client } }` (`mongoDBEventStoreConsumer.ts:184`) and the EventStoreDB processing scope sets `{ client, messageStore }` (`eventStoreDBProcessor.ts:96-100`). The EventStoreDB consumer gets a scope passing `{ session: { client, messageStore } }`.

### Q&A-2. MongoDB reactors and projectors get `messageStore` at runtime, while MongoDB and EventStoreDB types keep it optional

Quote: "Their own processors keep building it as today." / Q33 "it has to be consistent."
Consequence: The MongoDB reactor/projector scope spreads the consumer session (`mongoDBProcessor.ts:114-117`), so they newly receive it. `MongoDBProcessorHandlerContext` (`mongoDBProcessor.ts:44-50`) and `EventStoreDBProcessorHandlerContext` (`eventStoreDBProcessor.ts:38`) declare `messageStore?`.
Belongs to: qa
Resolution: fixed in r9. Precedent: SQLite and PostgreSQL declare it required (`sqliteProcessor.ts:92`, `postgreSQLProcessor.ts:102`), and Q33 made the in-memory one required for consistency. Once every store consumer passes it, MongoDB and EventStoreDB declare it required too. The new runtime value for MongoDB reactors and projectors is intended.

### Q&A-3. The "Extra work" note cites Q34 as approval, but Q34 never discussed cost

Quote: "Extra work: building that store object each time the consumer's scope runs ... Q34 allows it."
Consequence: A developer builds a store per batch citing an approval that doesn't exist.
Belongs to: qa
Resolution: fixed in r9. Precedent: PostgreSQL's consumer builds its scope context once (`postgreSQLEventStoreConsumer.ts:205-211`, used at :277); memory rule "decide at create time, not per call". Each consumer builds its `messageStore` once, when the consumer is created. No work is added per batch.

### Q&A-4. "One scenario per store" leaves the SQLite drivers open

Quote: AC 9.10 "(one scenario per store)" / AC 13.4 "SQLite (sqlite3, D1, Durable Objects)".
Consequence: SQLite in-memory hosting specs exist per driver.
Belongs to: spec
Resolution: fixed in r9. Precedent: `sqliteEventStoreConsumer.inMemory.projections.int.spec.ts` exists for sqlite3, D1 and Durable Objects; memory rule "replicate driver specs". AC 9.10 runs on each SQLite driver.

### Quality-2. How SQLite and PostgreSQL consumers build the store is not pinned

Quote: "They build it from the consumer's own connection, the same way their processors build it ... it opens no connection and runs no query."
Consequence: Processors build it from the transaction's connection with `schema: { ...options.migrationOptions, autoMigration: 'None' }` (`sqliteProcessor.ts:231-259`, `postgreSQLProcessor.ts:350-378`). Without `autoMigration: 'None'` the store migrates on first use; a wrong schema name sends appends elsewhere; when to build is open.
Belongs to: spec
Resolution: fixed in r9. Precedent: the processors' own construction. Each consumer builds the store from its pool with the consumer's event store schema options and `autoMigration: 'None'`, once at creation (see Q&A-3).

### Quality-4. What `inMemoryProcessingScope` does when no `session.messageStore` arrives

Quote: "`InMemoryProcessorHandlerContext` declares `session.messageStore: EventStore` as required" / "so in-memory processors they host always have it (Q34)".
Consequence: `session: partialContext?.session ?? {}` (`inMemoryProcessors.ts:182`) stops compiling. The session can still be missing for the generic `consumer(...)` without a scope (`consumers.ts:229-230`) or a direct `processor.handle(...)`. All existing uses of in-memory processors go through store consumers, which pass it after r9 (checked across `src/packages`).
Belongs to: qa
Resolution: fixed in r9. Precedent: the same scope throws `EmmettError` when `database` is missing (`inMemoryProcessors.ts:174-177`). It throws `EmmettError` the same way when `session.messageStore` is missing.
