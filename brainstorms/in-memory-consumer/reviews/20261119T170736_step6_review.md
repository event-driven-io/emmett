### Step-1. No test checks that `includeAsyncProjections` leaves inline projections out of the consumer

Quote: diff: `.filter(({ type }) => type === 'async')` and `if (consumerOptions?.includeAsyncProjections) for (const projection of asyncProjections) consumer.projector({ ... })`. spec.md:73: "`consumer({ includeAsyncProjections: true })` adds the async ones to the consumer as projectors, as PostgreSQL and SQLite do." Plan 9.4: "GIVEN an in-memory store with both inline and async projections WHEN events are appended THEN the inline projection runs during the append, as today."
Consequence: The only test that mixes inline and async registrations (9.4) never builds a consumer. Every test with `includeAsyncProjections: true` registers async projections only. If the filter broke and the consumer added every registration, each inline projection would run twice, once during the append and once as a projector, and every step 6 test would still pass. One check closes the gap: register both kinds, call `consumer({ includeAsyncProjections: true })`, and assert that `consumer.processors` holds only the async projector.
Belongs to: plan. spec.md:73 decides the behaviour ("adds the async ones"), but neither the step's test list nor spec.md or qa.md names this as a test case.
Resolution: fixed (Oskar: "Add test."). Added `consumer with includeAsyncProjections doesn't add inline projections` to `inMemoryEventStoreConsumer.asyncProjections.unit.spec.ts`; it asserts `consumer.processors` ids are exactly the async projector's. Checked it fails when the `type === 'async'` filter is removed.

### Standards-1. New TODO comment copied into the in-memory store

Quote: diff, `consumer` implementation: `// TODO: Fix this cast when projection registrations are typed with the consumer message type` above `projection: projection as unknown as InMemoryProjectorOptions<ConsumerMessageType & AnyEvent>['projection']`. AGENTS.md, Working rules: "Do not use comments inside the code unless asked. If you want to do it, review code and make it self-explanatory instead." The same comment is in `SQLiteEventStore.ts:532` and `postgreSQLEventStore.ts:755`.
Consequence: Step 6 adds a code comment that nobody asked for, which breaks an AGENTS.md rule. plan.md, spec.md and qa.md do not mention this comment; the only cast they name is the test-side `context.session.messageStore as EventStore`. Copying the comment matches the other drivers, so the AGENTS.md rule and the local convention conflict here. There are two options: drop the comment and keep the cast, or keep it to match SQLite and PostgreSQL. Oskar decides.
Belongs to: implementation
Resolution: kept (Oskar asked "Can this be easily fixed?"). No. Without the cast, `tsc` fails: registered projections are typed for `AnyEvent`, the consumer's message type is picked per `consumer()` call, and `eventsOptions.schema` (`EventStoreReadSchemaOptions`) makes the projection type invariant in its event type. Removing the cast needs the store to be generic over its projections' event types, in all drivers. The comment matches `SQLiteEventStore.ts` and `postgreSQLEventStore.ts`.
