### Step-1. No test checks that caller-given `storage` wins on `consumer.projector` and `consumer.workflowProcessor`

Quote: spec.md line 267: "MongoDB reactors, projectors and workflow processors get an optional `storage` option. The consumer's factories fill it with the consumer's `storage` when the caller gave none". Diff: `projectorFactory: (processorOptions) => mongoDBProjector({ ...processorOptions, storage: processorOptions.storage ?? options.storage })` and the workflow factory with `storage: processorOptions.storage ?? options.storage`. Only the reactor has a caller-given-storage test ("caller-given processor storage wins", 20.7). The projector and workflow checkpoint tests use only the storage that the factory fills.
Consequence: If either factory always wrote the consumer's storage (`storage: options.storage`) and dropped the caller's choice, a projector or workflow processor pointed at `other_db` would store its checkpoints (and, for the workflow, its outputs) in the consumer's database, and every test would still pass. The earlier Step-2 finding named this case; its fix covered only the filled case.
Belongs to: implementation. Spec.md line 267 decides "when the caller gave none" for all three processor kinds.
Resolution: fixed: added "caller-given projector storage wins" (checkpoint in `other_db`, none in `custom_db`) and "caller-given workflow processor storage wins" (workflow stream in `other_db`, empty in `custom_db`); each fails when its consumer factory ignores the caller's `storage`.

### Standards-1. The workflow checkpoint test only checks that a checkpoint exists, not its value

Quote: test "workflow processor checkpoint is in the custom database's emt:processors, not the default database": `assertOk(inCustomDatabase.lastCheckpoint);`. The reactor and projector checkpoint tests in the same file compare the full value: `assertDeepEqual(inCustomDatabase, { lastCheckpoint: handledCheckpoints[0] });`.
Consequence: The test passes when the workflow processor stores any non-null checkpoint in `custom_db`, for example a stale one or one from the wrong message. This breaks the local convention in the file and the project rule to assert full values, with partial match as the exception. The full check is possible: the test's `stopAfter` already receives the `GroupCheckoutInitiated` message, so it can record `message.metadata.checkpoint` and assert `{ lastCheckpoint: <that checkpoint> }` as the sibling tests do.
Belongs to: implementation
Resolution: fixed: the test now asserts `{ lastCheckpoint }` equals the checkpoint of the inbox input the workflow handled last. A reactor on the same consumer records it, because the workflow calls `stopAfter` on unrecorded output messages, which have no checkpoint.
