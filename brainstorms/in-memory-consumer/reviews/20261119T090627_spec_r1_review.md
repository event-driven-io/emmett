### Q&A-1. No answer chose the store's database for processor checkpoints; the standalone consumer's database is not specified

Quote: Spec: "The store's consumer gives them the store's database, so checkpoints and read models live in the same database as inline projections." / "When a processor's options don't name a database, the store's consumer passes the store's database." / "`workflowProcessor(...)` runs a real workflow processor ... with in-memory checkpoints." / "`inMemoryEventStoreConsumer({ source, messageStore, ...config })`" (no database option). Q&A: Q10 "using the in-memory store for workflow and output streams"; Q22/Q23 settle only `messageStore`. Code: `inMemoryReactor`/`inMemoryProjector` create a fresh database when `connectionOptions.database` is missing (`inMemoryProcessors.ts:192,225`); `inMemoryCheckpointer` falls back to its own `getInMemoryDatabase()` (lines 74–77).
Consequence: AC 2.5 and 8.1 hold only if the store's `consumer()` passes the store's database, which Oskar never confirmed. For the standalone factory a developer must guess between a fresh database per processor (today), a `database` option on the factory, or `messageStore.database` when it is an in-memory store. Workflow checkpoints have the same gap.
Belongs to: qa
Resolution: fixed in r3 (back to brainstorm: Q24 "yes, but only in memory store has database...", Q25 "Let's start with B...")

### Quality-1. How the store's database reaches processors is not decided, and the standalone factory cannot receive one

Quote: "The store's `consumer()` builds the consumer from the global log as its source, the store itself as its message store, and the store's `InMemoryDatabase` for processors." / "When a processor's options don't name a database, the store's consumer passes the store's database." / "Standalone factory: `inMemoryEventStoreConsumer({ source, messageStore, ...config })`" / "Config: the generic `MessageConsumerOptions`, plus `stopWhen.noMessagesLeft`, plus `pulling: { batchSize, batchDeadlineInMs }`"
Consequence: (1) `inMemoryReactor`/`inMemoryProjector` always create a database (`options.connectionOptions?.database ?? getInMemoryDatabase()`, `inMemoryProcessors.ts:192,225`), and `inMemoryProcessingScope` prefers it over the context one (line 172). Passing the store's database through the consumer `scope` context, as SQLite does (`sqliteEventStoreConsumer.ts:259-267`), is silently ignored. (2) The factory config has no database field, so the store's `consumer()` has no declared way to supply one. (3) The standalone default is unstated. (4) Workflow checkpoint database is unstated. Overlaps Q&A-1.
Belongs to: qa
Resolution: fixed in r3 (back to brainstorm: Q24, Q25 "Let's start with B, remember that inmemory consumer can get non-inmemory processors")

### Quality-2. The copied SQLite scenarios need `lastEventGlobalPosition`, which the in-memory append does not return

Quote: "Copy every SQLite consumer scenario that is not tied to SQL, keeping SQLite's scenario names and outcomes." / ACs 4.3, 5.5, 6.1, 8.2 "... THEN they have the same outcomes"
Consequence: In-memory `appendToStream` returns plain `AppendToStreamResult` (`inMemoryEventStore.ts:215,295-299`), without `lastEventGlobalPosition` (`eventStore.ts:235-242`). The SQLite suites read that field 23 times (handling 14, projections 4, inMemory.projections 4, awaiters 1 via `whenProcessed(appendResult.lastEventGlobalPosition)`). A developer must choose between changing the in-memory append result to `AppendToStreamResultWithGlobalPosition` (a public API change) or rewriting those scenarios without it.
Belongs to: qa
Resolution: fixed in r3 (back to brainstorm: Q26 "yes")

### Quality-3. AC 6.1 needs the store's `observability` to reach the consumer, but no decision says so

Quote: "6.1. GIVEN the observability scenarios that SQLite's consumer handling suite covers WHEN they run on the in-memory consumer THEN they have the same outcomes." / "`InMemoryEventStore` declares `consumer(options?)`. Its options are the in-memory consumer config plus `includeAsyncProjections?: boolean`"
Consequence: SQLite's scenario "a consumer created from an event store logs through the store's observability" (`sqliteEventStoreConsumer.handling.int.spec.ts:345-386`) passes because SQLite merges store and consumer observability (`SQLiteEventStore.ts:516-519`). The in-memory store takes `observability` too (`inMemoryEventStore.ts:64`), but no decision says its `consumer()` merges it, so a developer following the decisions fails AC 6.1.
Belongs to: spec
Resolution: fixed in r2 (Oskar: "ok")

### Quality-8. Decisions with no acceptance criterion

### Quality-10. Handler context for async in-memory projections is not defined

Quote: "`consumer({ includeAsyncProjections: true })` adds the async ones to the consumer as projectors" / "`reactor(...)` and `projector(...)` use the existing `inMemoryReactor` and `inMemoryProjector`."
Consequence: Inline projections get `{ eventStore, database, session, observabilityScope }` (`inMemoryProjection.ts:59-64`; type `InMemoryProjectionHandlerContext` with `eventStore?`, `inMemoryEventStore.ts:51-54`). Through `inMemoryProjector` they get `InMemoryProcessorHandlerContext` without `eventStore` (`inMemoryProcessors.ts:26-28,179-183`). A projection switched from `'inline'` to `'async'` loses `context.eventStore`; the spec doesn't say whether the store's consumer supplies it.
Belongs to: qa
Resolution: fixed in r3 (back to brainstorm: Q28 "ok")
