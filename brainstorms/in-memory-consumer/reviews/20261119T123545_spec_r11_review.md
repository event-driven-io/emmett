### Q&A-1. The MongoDB consumer's message source reads the default database, so `storage` reaches the message stores but not the source

Quote: Q36 resolution "every MongoDB `messageStore` ... is built from the client plus those options" / AC 9.11a.
Consequence: `mongoDBEventStoreConsumer` builds its source from `client` only (`mongoDBEventStoreConsumer.ts:154-159`); it watches `client.db(undefined)` (`mongoDBMessageSource.ts:49`, `:70`). With a custom `databaseName`, appends land elsewhere and the consumer never sees them. PostgreSQL passes its schema to the source too (`postgreSQLEventStoreConsumer.ts:198-203`).
Belongs to: qa
Resolution: fixed in r12 (back to brainstorm: Q37 "if it's a simple change do it now", Q38 "yes")

### Q&A-2. How MongoDB processors receive `storage` is not stated

Quote: "the consumer passes them to the processors it creates" / "builds `messageStore` from the processor's own client".
Consequence: No MongoDB processor, connection or consumer option has a storage field (`mongoDBProcessor.ts:59-64`, `mongoDBEventStore.ts:187-188`, `mongoDBEventStoreConsumer.ts:45-63`). PostgreSQL has a public optional `migrationOptions` on processors, filled by the consumer factories when missing (`postgreSQLProcessor.ts:319`, `postgreSQLEventStoreConsumer.ts:224-236`). Name, placement, standalone use and built processors are open.
Belongs to: spec
Resolution: fixed in r12 (Q38; optional `storage` processor option filled by consumer factories, PostgreSQL `migrationOptions` precedent)

## Quality

Checked: r9 findings against r11; spec Solution and ACs 9.10–9.13, 9.11a, decisions; `qa.md` Q33–Q36. Code as above plus `mongoDBSubscription.ts`, `inMemoryProcessors.ts`, `processors.ts`, `consumers.ts`.

### Quality-1. AC 9.11a names no storage value, and for some values the consumer never reads the event

Quote: AC 9.11a.
Consequence: The source ignores `storage` and keeps only collections matching `^emt:` (`mongoDBSubscription.ts:199`). With `databaseName: 'other'` or a non-`emt:` collection name, the AC can never pass.
Belongs to: spec
Resolution: fixed in r12 (AC 9.11a names `databaseName: 'custom_db'`; source follows `databaseName`)

### Quality-2. Only one of the three MongoDB scopes that must use `storage` has an AC

Quote: "Every MongoDB `messageStore`, whether in the consumer scope, the reactor and projector scope or the workflow scope ..." / AC 9.11a "a reactor on its consumer".
Consequence: The consumer scope (seen by in-memory processors), the workflow scope and the projector path stay untested with storage.
Belongs to: spec
Resolution: fixed in r12 (ACs 9.11b–9.11d cover MongoDB reactor, consumer scope via in-memory reactor, workflow)

### Quality-3. Whether the MongoDB workflow scope keeps building its store on each call

Quote: "It builds it once, when the processor is created, not on every call." (reactors and projectors only)
Consequence: The workflow scope builds per call today (`mongoDBProcessor.ts:140`); the spec doesn't say whether that moves to creation.
Belongs to: spec
Resolution: fixed in r12 (workflow scope builds once at creation, like reactors and projectors)
