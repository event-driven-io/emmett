### Step-1. `lastEventGlobalPosition` is read after the inline-projection `await`, so it can belong to another append

Quote: diff, `inMemoryEventStore.ts`:

```ts
globalLog.append(...storedEvents);
// Process projections if there are any registered
if (inlineProjections.length > 0) {
  await handleInMemoryProjections({ ... });
}
const result: AppendToStreamResultWithGlobalPosition = {
  nextExpectedStreamVersion: positionOfLastEventInTheStream,
  lastEventGlobalPosition: bigIntProcessorCheckpoint(
    BigInt(getAllEventsCount()),
  ),
```

Spec, In-memory store: "`lastEventGlobalPosition` is the checkpoint of the last appended event." It also says: "Extra work per append: one `append(...)` call on the global log and waking any waiting readers. Q8 and Q19 allow it."

Consequence: a scratch script with an async inline projection and `Promise.all` of two single-event appends to `s1` and `s2` returned `lastEventGlobalPosition` `…0002` for both, but the `s1` event is at global position `…0001`. So `whenProcessed(result.lastEventGlobalPosition)` can wait for an event of another append. It can also hang when that append fails. The second `getAllEventsCount()` also sums every stream's length on each append, which is extra work the spec does not allow. The fix is to take the value from `newEvents.at(-1).metadata.globalPosition`, or from the global log. No test covers concurrent appends with an async inline projection.
Belongs to: implementation
Resolution: fixed. The append captures the event count once, before building the events, and returns `allEventsCount + events.length`; this also drops the per-event stream sum. New test "each concurrent append returns the global position of its own last event".

### Step-2. The in-memory reactor and projector now handle `checkpoints: 'DISABLED'` differently, and neither the step nor the spec decides this

Quote: diff, `inMemoryProcessors.ts`:

```ts
>(options?: { database?: InMemoryDatabase; }) ... options?.database ?? (context as ...)?.database ?? ...
checkpoints:
  options.checkpoints === 'DISABLED'
    ? inMemoryCheckpointer<MessageType>({ database: getInMemoryDatabase() })
    : inMemoryCheckpointer<MessageType>(),
```

The same change is made in `inMemoryProjector`. Step: "No new options on `inMemoryReactor` / `inMemoryProjector` (Q32)." Nothing in the step, spec.md or qa.md mentions `DISABLED` or `inMemoryCheckpointer`'s signature.

Consequence: the implementer's note is correct. Before this change, both processors overwrote `options.checkpoints` and stored checkpoints in the processor's or the context's database. With the message-store rule, that database is the store's, so the copied "does not persist a … checkpoint across a restart when checkpoints are DISABLED" scenarios would fail. The fix changes the behaviour of the existing public `inMemoryReactor` and `inMemoryProjector`, even for standalone use: a DISABLED checkpoint no longer shows up in `processor.database`. It also adds a public option to the exported `inMemoryCheckpointer`. Oskar should approve both. The step should name this change.
Belongs to: plan
Resolution: kept as implementation. Spec 2.12 decides the behaviour: the copied "does not persist a reactor/projector checkpoint across a restart when checkpoints are DISABLED" scenarios must have SQLite's outcomes, and they fail with the store's shared database unless DISABLED uses a private database. No option is added to `inMemoryReactor` / `inMemoryProjector` (Q32); `inMemoryCheckpointer` gets an optional `database`. Reported to Oskar for confirmation.
