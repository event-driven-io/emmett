### Q&A-1. "Metadata read as text" does not match the committed PostgreSQL read

Quote: Read rule "PostgreSQL reads the metadata value as text (`metadata->>'schemaVersion'`), so the JSON number `2` and the string `'2'` both read as `2`."; Q108 "a JSON number `2` in PostgreSQL metadata reads as `2` (metadata read as text)". Code: `readStream.ts:59` selects the whole `message_metadata`; `isNumericSchemaVersion` (`schemaVersion.ts:1`) accepts any integer number.
Consequence: a developer has to guess whether to add `metadata->>'schemaVersion'` to the read SQL or keep the TypeScript parse. They differ for a JSON number such as `-1`: `'-1'` through `->>` reads as `1`, the current code reads `-1`.
Belongs to: spec
Resolution: fixed in r10 (Oskar, Q113: "yes"). Read rule follows the committed code; the `->>` sentence is gone.

### Q&A-2. Old append function after a failed migration

Quote: "first replaces the old append function, in its own transaction, with a converting body … Then it changes the column in a second transaction."; 16.15 "fails with an error AND the column is still `TEXT` with unchanged data"; 14.3 "GIVEN a `TEXT` column WHEN the old append function gets `'v2'` THEN the column holds `'v2'`".
Consequence: the first transaction has committed when the `ALTER` fails, so the store has a `TEXT` column with the converting body, and 0.43.0 appends of `'v2'` fail, against 14.3. The same holds after a timeout (16.12) and possibly a dry run (16.11).
Belongs to: spec
Resolution: fixed in r9 by Q112 (Oskar: "ok, let's do a"). The column migrations no longer replace the body, so a failed, timed-out or dry run leaves the converting body the automatic migration already set; 14.3 now expects `'v2'` to fail.

### Quality-1. EventStoreDB fallback has no criterion

Quote: 6 "In EventStoreDB, `metadata.schemaVersion` is the stored version itself, so 4.1 covers it."; Read rule "stored value if numeric, else `1`".
Consequence: 4.1 covers only a numeric `2` written by the current release. Nothing checks that old EventStoreDB events without `schemaVersion`, or with `'2'` or `'v2'`, read as `1`, `2` and `1`.
Belongs to: spec
Resolution: fixed in r10 (Oskar, Q113: "yes"). Criterion 6.8.

### Quality-2. Digits-only rule on values stored as numbers

Quote: "A value is numeric when it is made of digits only … `'-1'` … is non-numeric"; 7 "User appends values that are not positive integers, so that appends do not add validation"; "No validation of the value."
Consequence: `schemaVersion: -1` can be appended. A developer has to choose whether the digits rule applies to stored numbers too (then it reads back as `1`) or only to strings (it reads back as `-1`). The same goes for `1.5` in MongoDB or in-memory. 7.1 tests only `0`.
Belongs to: qa
Resolution: fixed in r10 (Oskar, Q113: "yes"). Whole numbers stored as numbers are taken as they are, the digits rule is only for strings; criteria 7.2 and 7.3.

### Quality-3. Tetris with a user CASE on an INT column has no criterion

Quote: "copies all rows through the same `COALESCE`, also when the column is already `INT`, so a given user `CASE` applies"; 18.3 "GIVEN a `TEXT` column"; 18.4 "without a user `CASE`".
Consequence: an implementation that skips the `CASE` on an `INT` column passes every criterion.
Belongs to: spec
Resolution: fixed in r10 (Oskar, Q113: "yes"). Criterion 18.13.

### Quality-4. Too-large values on read and two untested paths

Quote: "A digits-only value too large for an `INT`, such as `'99999999999'`, fails the cast: a migration stops with an error … A 0.43.0 append that sends it fails with an error."; 16.15.
Consequence: the spec does not say what a read returns for such a value on a `TEXT` column or in metadata: the number, a fallback, or an error. With 20 or more digits the JS number loses precision. A 0.43.0 append of it and the tetris migration meeting it have no criterion.
Belongs to: qa (read), spec (criteria)
Resolution: fixed in r10 (Oskar, Q113: "yes"). Reads return the parsed number and never fail; criteria 6.7, 14.6 and 18.12.

### Quality-5. Two transactions do not fit one Dumbo run

Quote: "Every migration that changes the column to `INT` first replaces the old append function, in its own transaction … Then it changes the column in a second transaction."; "They run through the regular migration run like the other migrations."
Consequence: Dumbo's `runSQLMigrations` applies all pending migrations in one `pool.withTransaction`, and Emmett's schema run wraps the run in a transaction (`emmett-postgresql/src/eventStore/schema/index.ts:93`). A developer has to choose: two separate Dumbo runs (two migration names, each with its own self-check and dry run), or one run that loses the guarantee in 13.5 and 13.6. The same applies to the mandatory migration once it is in the 0.44.0 automatic set.
Belongs to: spec
Resolution: fixed in r9 (Oskar, Q112: "ok, let's do a"). The automatic migration of the current release gives the old function the converting body; the column changes do not touch it and run in one transaction.
