### Step-1. "a second run changes nothing" does not do what the step says

Quote: Plan: "19.7: ... after the first `createEventStoreSchema`, `UPDATE` one row's column to `3`, then call `createEventStoreSchema` again; asserts the second run applies no migration, and the layout and every row, including the `3`, are unchanged." Test: `runSQLMigrations(pool, migrations_0_43_0)` twice, with no `UPDATE`, and asserts `applied` empty, `skipped` equal and `allMessages` equal.
Consequence: no row holds a version that differs from its metadata, so a re-run of the swap SQL would still give the same rows. If Dumbo stopped skipping the migration, the test would pass. The layout is not compared.
Belongs to: implementation
Resolution: fixed (confirmed in 20261111T181500_step12_review.md)

### Step-2. The read-rule extra test misses three listed cases and adds one

Quote: Plan: "metadata `schemaVersion` as the number `3`, the number `-1`, the number `0`, `'02'`, `''`, `' 2'` and `'2.0'`; asserts `3`, `1`, `0`, `2`, `1`, `1` and `1`". Test "takes a whole JSON number in metadata as it is": rows `3`, `1.5`, `-1`, `0`, `'02'`; asserts `[3, 1, 1, 0, 2]`.
Consequence: `''`, `' 2'` and `'2.0'` are not run. Removing `AND ... NOT GLOB '*[^0-9]*'` from the migration would turn `'2.0'` into `2` (SQLite `CAST` reads the leading digits) and every test would still pass. `''` and `' 2'` are stopped by the first `GLOB` and are unguarded too. The test name also differs from the plan's.
Belongs to: implementation
Resolution: fixed (confirmed in 20261111T181500_step12_review.md)
