# Review: spec r1

Reviewed: `spec.md` r1, `qa.md` up to Q104. Earlier reviews: None saved. Two earlier rounds ran before review files existed. This review ran with the old briefs, before the shared rules, so the reports had no `Checked:` line and no consequence for each finding. The quotes and consequences below are taken from the two reports.

## Q&A

Checked: the spec against Q76, Q81, Q84, Q87, Q89, Q90, Q94, Q98, Q100, Q101 and Q104, and the projection `version` columns in `src/packages/emmett-postgresql/src/eventStore/schema/tables.ts:72` and `src/packages/emmett-sqlite/src/eventStore/schema/tables.ts:51`.

### Q&A-1. EventStoreDB read contradicts 6.5

Quote: "stored in the event metadata under `schemaVersion`"; read rule "stored value if numeric, else `1`", "`'2'` is `2`"; 6.5 "6.5 for MongoDB, EventStoreDB and in-memory ... `metadata.schemaVersion: '2'` ... `schemaVersion` is `1`".
Consequence: in EventStoreDB the stored value and the metadata key are one field, so the read rule gives `2` and 6.5 gives `1`. A developer cannot satisfy both.
Belongs to: spec
Resolution: fixed in r2 (Oskar: "go ahead"). 6.5 now covers MongoDB and in-memory only.

### Q&A-2. Q71 events form became firm without confirmation

Quote: Q71 "if that works then fine, same for events if that's overcomplicating then just 2"; spec "Events have no extra form."
Consequence: `event<V2>(type, data, undefined, 2)` is ruled out without Oskar choosing it.
Belongs to: qa
Resolution: rejected (Oskar: "dude, seriously? was my answer on this uncear?"). Q71 already says to do the same for events only if it works without overcomplicating. The research found that events without declared metadata have no metadata position today, so the `undefined` form would be a new form, and the spec keeps `event<V2>(type, data, 2)`.

### Q&A-3. Q104 "regular" read as the mandatory migration

Quote: Q104 "(both odemand and regular)"; spec sets `ignoreHashMismatch: true` on the on-demand migrations and the mandatory one.
Consequence: if "regular" meant the automatic migrations of the current release, they are left without `ignoreHashMismatch`.
Belongs to: qa
Resolution: rejected (Oskar, Q105: "The one in 0.44.0"). The spec already sets it on the mandatory migration.

### Q&A-4. Q93 question about adjusting procedures in 0.44.0 unanswered

Quote: Q93 "In 0.44.0 we can again adjust old and v0.43.0 procedure, right? Or even in the column type migrations…"; spec "its body never changes".
Consequence: the spec fixes the new function's body forever, while Oskar's question is open.
Belongs to: qa
Resolution: fixed in r3 (Oskar, Q106: "Yes"). The body does not need to change when the column type changes, and a later migration can still replace either body.

### Q&A-5. What a downcaster returning V1 | V2 stores

Quote: Q73 "downcast should be able to provide also v1 & v2 compatible".
Consequence: neither the spec nor Q76 says which version such a downcaster stores.
Belongs to: qa
Resolution: fixed in r4 (Oskar, Q107: "yes"). Q76 answers it; criterion 9.3 added.

### Q&A-6. Values above INT and the '02' rule

Quote: "Values too large for an `INT` are not handled separately."; "`'02'` is `2`"; first Q96 reading "`'02'` … non-numeric".
Consequence: a digits-only value above 2147483647 fails the cast in the `ALTER ... USING`, the tetris `COALESCE` and the converting append, aborting the migration or the append. No answer covers it. The spec does not say it chose the easier rule for `'02'` on purpose.
Belongs to: qa
Resolution: fixed in r6 (Oskar, Q109: "1"). The value fails the cast, the user maps it with their `CASE`; criterion 16.15. The `'02'` rule follows Q96 ("whatever is the easiest") and is pinned by 6.6.

### Q&A-7. 0.44.0 stall risk has no decision

Quote: Further Notes "the first 0.44.0 instance starts the table rewrite under `ACCESS EXCLUSIVE`, and any 0.43.0 instances still serving stall until it ends."
Consequence: stated as a risk, with no decision and no out-of-scope or follow-up entry.
Belongs to: qa
Resolution: rejected (Oskar, Q111: "I thill don't understand why are you asking"). The Further Notes already describe the risk and the advice.

## Quality

Checked: not given. The report went through briefs (a) to (h) over the whole spec.

### Quality-1. How the tetris migration checks whether it has to run

Quote: "Each checks itself whether it has to run"; 18.4 "the existing `INT` values are kept".
Consequence: "column is already `INT`" is not enough, because 18.4 still rebuilds the layout. The developer has to choose: compare column order, compare against the full fresh layout, or something else.
Belongs to: qa
Resolution: fixed in r7 (Oskar, Q110: "check one column"). It runs unless `message_schema_version` is `INT` and right after `created`; criterion 18.11.
