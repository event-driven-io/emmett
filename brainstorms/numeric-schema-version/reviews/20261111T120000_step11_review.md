### Step-1. Lock waits in 13.5 and 16.14 can pass without the lock being observed

Quote: `waitForLockWaiters`: `for (let attempt = 0; attempt < 100; attempt++) { ... if (Number(rows[0]!.waiting) >= expected) return; await ...50ms }` falls out silently after 5 s. Step 13.5: "poll `pg_stat_activity` every 50 ms until a backend running the `ALTER` has `wait_event_type = 'Lock'`".
Consequence: the count is database-wide, not the `ALTER` backend, and nothing fails if the wait is never reached. The tests can release the lock early and pass without the append waiting behind the `ALTER`, or without two runs overlapping.
Belongs to: implementation
Resolution: open

### Step-2. Read-rule SQL gaps that no test catches

Quote: `COALESCE(<user>, <column>, <metadata>, 1)`, `CASE WHEN message_schema_version ~ '^[0-9]+$' THEN message_schema_version::int END`. Spec read rule: "`'02'` is `2`... `'2.0'`, `'-1'`, `' 2'` or `'v2'` ... missing"; JSON number "whole number of `0` or more".
Consequence: swapping column and metadata order, changing `>= 0` to `> 0`, or widening a regex would pass all tests. No row has a numeric column with a different numeric metadata value, metadata `0`, or column `'02'`, `'2.0'`, `'-1'`, `' 2'`.
Belongs to: implementation
Resolution: open
