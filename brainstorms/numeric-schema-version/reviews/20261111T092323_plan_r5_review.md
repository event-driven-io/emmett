### Spec-1. Step 10 tests 14.1's INT half on a new store, while 14.2's INT half, which has the same GIVEN, moves to step 11 because it needs the migration

Quote: spec 14.1 "GIVEN a store upgraded to the current release WHEN the current release appends an event with `schemaVersion: 2`, once on a `TEXT` column and once on an `INT` column THEN both appends succeed". Spec 14.2 has the same GIVEN. Plan step 10, 14.1 test: "a released 0.43.0 store after the automatic migrations, and a new store". Plan step 10, 14.2: "Part: the `TEXT` column. Step 11 covers the `INT` column, which needs the schema version migration." Plan step 10, 24.1 test: "then the 14.1, 14.2 (TEXT) and 15.1 to 15.3 scenarios in that schema".
Consequence: the plan reads one GIVEN in two ways. For 14.1, a new store stands in for an upgraded store with an `INT` column. So no step lists the case where the current release appends through the new function on an upgraded store after the `ALTER` changed the column. 16.8 happens to append `4` there, but it is not labelled as 14.1. Inside 24.1, the implementer has to guess whether "the 14.1 scenarios" in a custom schema include a fresh custom-schema store for the `INT` half, or only the `TEXT` half, as for 14.2.
Belongs to: plan
Resolution: fixed in r6 (Oskar: "ok").

### Steps-4. The 16.14 test does not make the two migration runs overlap

Quote: "16.14: 'two runs started together both succeed' - `Promise.all` of two calls on separate pools; asserts both resolve and the 16.1 values."
Consequence: `Promise.all` starts both calls, but nothing holds the first run until the second one waits on it. Compare 13.5, which uses a lock and polls `pg_stat_activity`. On a small store, the first run can commit before the second one starts. Then the test passes without a real overlap, and a missing migration lock, or a type check made before the lock wait, goes unnoticed. The plan does not say how to force the overlap, for example by holding a lock with a third pool and polling until both runs wait.
Belongs to: plan
Resolution: fixed in r6 (Oskar: "ok").
